# Absence as a general observation feature

Replace the apf2-specific `data.absenz` marking with a first-class `absence` boolean on observations, configurable per import, visible in tree, list and map.

**No migration paths**: per your call, existing databases are not updated — backend-dev (and the preview production) are rebuilt from the init files instead (`cd backend-dev && docker compose down -v && docker compose up -d --build`). Schema changes therefore go into the CREATE TABLE definitions only; no `ADD COLUMN IF NOT EXISTS` ALTERs, no SqlInitializer heal block. Installed browser clients need a local reset (clear local data / re-login) after the backend rebuild.

## How absence derivation is stored and re-applied (the core mechanism)

The absence rule lives **as columns on `observation_imports`** — the import row documents how absence was derived, exactly like `geometry_method`/`x_coordinate_field`/`label_creation` document geometry and labels:

- `absence_method observation_imports_absence_methods_enum` — `NULL` (no absence handling) | `'boolean_column'` | `'sql_expression'`
- `absence_field text` — the data column used in boolean_column mode
- `absence_expression text` — the SQL boolean expression used in sql_expression mode (e.g. `data->>'ANZAHL' = '0'`)

Re-application, mirroring how geometry/labels behave:

1. **Apply button** ("Absenzen setzen") in the new wizard tab sets `absence` for the import's observations and can be re-run any time after changing the rule.
2. **Re-import**: `updateObservations.ts` — both "Ersetzen" (replace) and "Aktualisieren und erweitern" (update-and-extend) — re-applies the **stored** rule to all rows after import, so observations added later get their absence derived by the same expression, with no re-entry of the rule.
3. Changing the rule in the tab resets `absence` to false for the import (like changing geometry config nulls geometries), so the next apply re-derives everything consistently.
